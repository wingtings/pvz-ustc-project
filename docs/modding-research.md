# 改版技术调研

## 结论

这个项目最稳妥的重启方式是固定 `1.0.0.1051` 基线，先完成文案和槽位换皮，再做可重复的常量补丁，最后只给少数招牌机制写钩子。暂时不要扩展植物或僵尸数量，也不要把某个教程中的十六进制地址直接抄进仓库。

经典 PC 版的资源和规则没有统一的现代模组接口。贴图、文本、动画和战斗逻辑分散在不同位置，所需技能也不同。中文社区通常把只动资源的作品称作 PAK，把修改玩法的作品称作改版。两者在完整项目中会同时出现。

| 类型 | 主要位置 | 适合做什么 | 推荐工具 | 难度 |

## 需要补齐的技能

| 技能 | 达到什么程度才够用 | 在本项目中的练习 |
| --- | --- | --- |
| 文本编码与差异审查 | 能分辨 UTF-8、GBK，能读懂逐行 diff，知道控制标记不能改 | 完成第一章图鉴同步并通过键名检查 |
| 透明位图编辑 | 会处理透明通道、固定画布、边缘抗锯齿和导出设置 | 以后替换绿圈科豆的一个头部部件 |
| 二维骨骼动画 | 看懂轨道、关键帧、父子部件、锚点和循环段 | 让改过头部的绿圈科豆完成待机与发射 |
| 32 位 x86 基础 | 看懂常见寄存器、栈、条件跳转和调用约定 | 跟踪一次费用读取，不写入任何数据 |
| 动态调试 | 会找访问者与写入者，区分动态对象地址和模块偏移 | 找到专注值变化的调用路径并跨关卡复现 |
| 静态分析 | 能识别函数边界、交叉引用、数据表和代码洞 | 在定义表中确认一个卡片费用与冷却 |
| 补丁工程 | 会校验哈希、检查旧字节、回滚和生成改动清单 | 让 75 专注的测试补丁能一键应用和撤销 |

不需要先把每项学到很深。顺序应跟版本走：v0.2 先处理编码和文案，v0.3 再进入 x86 与补丁工程，v0.4 才写逻辑钩子。绘画和动画等到资源清单确定后再开始。

### 文本

`LawnStrings.txt` 保存大多数界面文字和图鉴内容。现有文件已经改过部分植物名、敌人名、胜利提示和 GPA 树文字。继续编辑时要保留方括号键名和花括号标记，不要用常规格式化工具重排。

建议把可读的 UTF-8 草稿放在 `docs` 中，确认后再同步到 GBK 游戏文件。直接把 `LawnStrings.txt` 转成 UTF-8 会导致当前汉化版显示乱码，严重时还会让解析器在错误字节处中止。

每次同步至少检查以下内容：

1. 键名没有重复或丢失。
2. `{SHORTLINE}`、`{KEYWORD}`、`{STAT}`、`{FLAVOR}` 等标记原样保留。
3. 图鉴中的手工换行没有把一个 GBK 双字节字符拆开。
4. 所有新增字符都能被当前字体显示。
5. 选卡、商店、小游戏和通关后的同义文案一起更新。

### PAK 和静态资源

`main.pak` 是 PopCap PAK。仓库中的包使用常见的逐字节 `0xF7` 异或外层，解码后的文件头和记录表可以被现有工具处理。不要手工对整个文件做查找替换。

[PopStudio](https://github.com/PopGameTool/PopStudio) 支持 Windows PAK 的打包与解包，也支持 `reanim.compiled`、`xml.compiled`、粒子和拖尾等格式的转换。[PvZ Toolkit](https://github.com/lmintlcx/pvztoolkit) 支持多种官方 PC 版本，并提供常用辅助与 PAK 功能。项目应从这两个开源来源获取工具，不把来历不明的"修改器合集"提交进仓库。

资源替换要遵守原画布和锚点。PvZ 的角色通常由很多透明 PNG 部件组成，动画轨道引用的是部件名。只把整张角色图盖上去，待机时看似正常，攻击、受伤、掉头和死亡时通常会散架。

一个安全的静态资源循环如下：

1. 从干净基线解包到仓库外的工作目录。
2. 只复制要修改的文件到素材源目录。
3. 保留文件名、大小写、透明通道和画布尺寸。
4. 打包前生成改动清单，不把整个解包目录视为成品。
5. 启动游戏检查菜单、图鉴、实战、死亡动画和小游戏。
6. 发布时只交付自制资源或差分补丁。

### reanim 动画

`reanim` 目录多为动画部件贴图，真正的轨道数据通常在 `compiled/reanim`。PopStudio 可以在已支持的 reanim 格式、XFL 工程和现代 FLA 之间转换。传统教程也常用 Adobe Animate 加 JSFL 导出，再把 `.reanim` 编译成 `.reanim.compiled`。

动画修改最常见的崩溃原因是轨道名丢失、帧数不一致、引用了未打包的图片，或者用了错误平台的 compiled 格式。首个动画试验应选绿圈科豆，只改一个头部和一片叶子，依次验证 `anim_idle`、`anim_shooting`、眨眼和受伤状态。这个试验通过后再处理复杂僵尸。

### 常量补丁

反编译项目中的 `gPlantDefs` 表明，费用、卡片冷却和基础发射间隔集中在植物定义中。普通植物初始化为 300 耐久，出恭墙和大出恭墙分别使用 4000 和 8000。敌人则从 270 基础耐久起步，再叠加路障、铁桶和铁门等装备。[植物定义表](https://github.com/SammyZach/re-plants-vs-zombies/blob/cfabf8b1b89886e85ef514e7db443c6425fd9181/Lawn/Plant.cpp)和[敌人定义与初始化](https://github.com/SammyZach/re-plants-vs-zombies/blob/cfabf8b1b89886e85ef514e7db443c6425fd9181/Lawn/Zombie.cpp)是很好的结构参考，但它们是社区反编译成果，不是当前汉化文件的自动符号表。

费用、冷却和单个血量值适合先做 S2 补丁。实现时不保存 CE 运行中的临时地址，而是找到模块内的固定偏移或稳定特征码。补丁清单至少要记录：

```text
补丁名：P07 双发科豆费用
目标文件 SHA-256：6F1729...
定位方式：固定文件偏移或唯一 AOB 特征
预期旧字节：...
写入新字节：...
回滚字节：...
验证关卡：1-8、我是错题模式、坚果保龄球
```

十六进制编辑器看到的是文件偏移，调试器看到的通常是映像基址加相对虚拟地址。网上常见的"CE 地址减去 `0x400000`"只对部分无重定位的 32 位构建和相应区段成立，不能当成通用换算规则。

### 逻辑钩子

暖气片范围减速、GPA 结算和 DDL 空投扣分都不是改一个常量就能完成。它们需要找到稳定的更新或结算函数，保存被覆盖指令，跳到自建代码，再返回原流程。

建议采用这个调查顺序：

1. 用 CE 观察状态变化，确认对象和字段。
2. 找到读写该字段的指令，并在多个关卡复现。
3. 在 x32dbg、Ghidra 或 IDA 中确认函数边界、寄存器用途和调用约定。
4. 写最小钩子，只记录事件，不改变玩法。
5. 加入机制逻辑，再测试暂停、加速、重开和退出关卡。
6. 把补丁固化成带旧字节校验的构建步骤。

OllyDbg 仍能帮助理解很多旧教程，但日常调试可以换成 x32dbg。工具选择不是重点，重点是不要跳过函数边界和版本验证。

## 推荐学习顺序

### 1. 认识文件和完成一次文案修改

[超详细！植物大战僵尸改版教程 #1](https://www.bilibili.com/video/BV1TK421k7ar/)在前四分钟演示准备、图片和文字修改，后半段用单个阳光数值展示 CE 定位。先看它，可以把资源修改和代码修改的边界弄清楚。

[一代 PAK 文件解包教程](https://www.bilibili.com/video/BV1JQ4y1k7KS/)适合快速认识 `main.pak`。实际项目仍应使用能追溯来源的 PopStudio 或 PvZ Toolkit，并给干净基线留哈希。

### 2. 学会找值、找指针和验证指令

[豪哥修改教程补档合集](https://www.bilibili.com/video/BV1te4y1U7Jn/)有 67 节，覆盖阳光、卡槽、植物和敌人生成函数、出怪列表、随机弹丸、穿透、追踪以及多种状态。它适合按问题查阅，不适合一口气照抄。项目最先需要的是阳光、基础数据、出怪列表和僵尸速度几节。

[创建第六大关与更改地图](https://www.bilibili.com/video/BV1ya4y1Y7Yi/)展示了关卡和场景修改的思路。五章换皮完成前不建议真加第六章，但这段内容有助于理解为什么 S4 的成本明显高于改出怪表。

### 3. 处理动画

[最详细的 PvZ 动画修改教程](https://www.bilibili.com/video/BV1oJhXzMEXS/)集中讲自制植物、僵尸模型与 reanim 工作流。观看时要把软件操作和文件格式分开理解，因为工具版本会变化，轨道名、帧长和资源引用这些约束不会跟着视频界面变化。

### 4. 从教程过渡到可维护补丁

B 站教程解决"怎样让一次修改生效"，项目还要解决"怎样在另一台机器、另一次构建和一次失败后恢复"。这一步需要补上 Git、哈希、AOB 特征、补丁清单、自动回滚和回归测试。没有这些，CE 表和手工改过的 EXE 很快就会变成无法解释的历史文件。

## 两条长期路线

### 继续补丁原版

优点是和当前仓库、汉化文案、原版存档及既有教程最接近。缺点是地址固定、调试困难，新增槽位和界面很贵。v0.2 至 v0.4 应使用这条路线。

### 转向可编译的社区反编译项目

[re-plants-vs-zombies](https://github.com/SammyZach/re-plants-vs-zombies)把大量规则还原成可读 C++，也在替换旧渲染和平台代码。它更适合远期增加植物、敌人和脚本，但当前分支以 GOTY 数据和跨平台构建为主，和本仓库的汉化一版不是直接替换关系。迁移前要单独验证资源格式、存档、字体、音频和许可边界。

现阶段可以把它当结构资料，不要同时维护"原版二进制补丁"和"完整源码移植"两套实现。

## 测试和发布

每个修改都要在干净副本上重现。最低测试范围包括：

- 冒险模式的白天、夜晚、水池、雾夜和屋顶各一关。
- 图鉴、选卡、商店、禅境花园和制作人员页面。
- 对应植物的种植、攻击、受伤、睡眠、铲除和模仿者版本。
- 对应敌人的入场、特殊动作、失去装备、死亡和被魅惑状态。
- 坚果保龄球、我是错题、砸报告和无尽模式等会复用槽位的小游戏。

公开发布前，建议生成"玩家自备原版文件后应用"的补丁，不把 `PlantsVsZombies.exe`、`main.pak`、原音乐或整套原贴图打进发行包。仓库当前保留了去年的历史文件，本轮不擅自删除；正式公开前应单独做一次版权和仓库历史审查。
