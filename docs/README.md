## 状态词

进度使用以下状态；版本编号用于标记工作范围，不能替代验收状态。

| 状态 | 含义 |
| --- | --- |
| 设计完成 | 规则或资源规格已写清，尚不代表游戏中可用 |
| 已实现 | 已有代码、游戏文案或可生成的素材；注明在原版还是独立原型中 |
| 局部验证通过 | 特定构建、动作或场景有证据，其余范围仍待验收 |
| 完整验收通过 | 对应工作轨道的全部验收条件已有记录 |
| 远期 | 尚未排入当前交付范围 |

沿用编号：v0.2 文案、v0.3 常量、v0.4 逻辑机制、v0.5 视觉、v0.6 关卡。它们存在交叉推进，目前没有对应 GitHub Release；具体执行顺序以[路线图](roadmap.md)为准。

技术实现也分成五层。

| 层级 | 工作内容 | 典型例子 |
| --- | --- | --- |
| S0 | 只改 GBK 文案 | 名称、提示、图鉴文字 |
| S1 | 替换资源 | PNG、JPG、声音、已有动画部件 |
| S2 | 修改固定数值 | 费用、冷却、耐久、伤害 |
| S3 | 修改流程或状态机 | 暖气片减速、GPA 评级、成功空投扣分 |
| S4 | 扩展游戏结构 | 新槽位、新图鉴页、新关卡类型 |

## 当前设计决定

1. 第一阶段固定使用仓库中的 PC 版 `1.0.0.1051`。不同版本的地址和数据布局不能混用。
2. v0.2 采用槽位替换。原植物或僵尸的行为能表达新概念时，就保留原行为，只换名称、文案和视觉。
3. 战斗资源暂定名为"专注值"，对应原版阳光。GPA 是关卡结算指标，不直接拿来种植单位。
4. 敌人是课程、作业和截止日期形成的模拟异常，不影射具体教师、同学或行政人员。
5. 旧稿里的"柯南"统一改成"科豆"或"蝌蝻"。这样仍保留校内口吻，也不会让人误以为项目混入了另一部作品的角色。
6. 旧日志写了"数院、物院、花园、计算机、生院"。本稿把第三关暂定为"化院花园"，既保留"花园"这个原词，也让水池和化学实验主题能够接起来。如果旧稿原意确实是纯校园花园，只需改世界名称，不影响槽位设计。

## 文档如何进入游戏

植物和敌人文档是文案来源；当前同步工具已经把 49 个植物、26 个敌人的名称、提示和图鉴内容写入 `LawnStrings.txt`，并检查重复同步不会产生变化。后续修改仍需：

1. 通过[文案同步工具](../tools/README.md)生成，并根据实际文本框宽度检查、调整换行。
2. 保留 `{SHORTLINE}`、`{KEYWORD}`、`{STAT}`、`{FLAVOR}` 等控制标记。
3. 使用 CP936/GBK 与 CRLF 保存，并逐页检查中文字体、标点和溢出；自动检查通过不能替代这一步。

数值表写的是设计目标。标注"沿用原槽位"的项目，v0.2 不需要改可执行文件；标注 S2 或 S3 的项目，要在对应版本进入实现阶段后才算完成。
